# Архитектура

## Что уже решено

| Решение | Почему |
|---|---|
| Свой движок не пишем | 40–100+ человеко-лет и нет доступа к Widevine |
| WebView2 evergreen | Edge-рантайм уже стоит на Windows 10/11, обновляется сам, DRM в нём штатный |
| Rust + Tauri 2 | тот же стек, что у Ninety: общий опыт, общая сборка, общий инсталлятор |
| Electron исключён | второй Chromium в комплекте и память, которой у нас и так мало |
| Chrome браузера — веб-UI | подход Vivaldi: интерфейс правится без перекомпиляции, темы — те же токены, что в Ninety |
| ~30–40% движковой части — сырой COM | Tauri/wry закрывают одно окно с одним вебвью; вкладки, фильтр и раскладка — мимо их API |

## Процессная модель

```
190x4-browser.exe                    ← один процесс приложения
├── окно chrome      (webview #0) ← Tauri-вебвью, ui/, Tauri-IPC
│   ├── popup--chrome (webview)   ← меню, пузыри, окна страниц
│   └── вкладки (webview #1..N)   ← наш код, свой HWND-контейнер
├── окно chrome-2 …              ← второе окно: свой хост, свой попап
│       │
│       └── msedgewebview2.exe ×M ← браузерный процесс + GPU + рендереры (общие на все окна)
```

Ключ ко всей экономии памяти — **один `ICoreWebView2Environment` на все вебвью**.
Мы не создаём его сами: Tauri уже создал Environment для chrome-вебвью, и мы
достаём именно его (`interop::environment_of`). Попытка сделать «второй
Environment с такими же параметрами» разводит нас на два браузерных процесса:
WebView2 переиспользует процесс только при полном совпадении user data folder
и browser arguments, а Tauri свои аргументы добавляет молча.

## Окна

Окон браузера может быть несколько (`src-tauri/src/browser_windows.rs`). Каждое —
свой `TabHost` со своим контейнером вкладок и своим всплывающим окном
(`popup--<ярлык>`), но `ICoreWebView2Environment` у всех общий: второй
Environment развёл бы окна по разным процессам движка.

* Номера вкладок и загрузок глобальные. Команда знает только номер, а окно
  ищется по нему (`state::with_tab`, `with_download`) — так интерфейсу не нужно
  передавать ярлык окна в каждом вызове.
* События вкладки уходят `emit_to(ярлык)`: событие чужого окна не должно
  перерисовывать это. **Подписка JS в Tauri по умолчанию слушает все окна** —
  `emit_to` доходит и до слушателей без адресата. Поэтому `ui/js/bridge.js`
  подписывается только на своё окно (`target: AnyLabel`), а попап и его окно
  обмениваются событиями `emitTo` друг другу. Без этого меню второго окна
  рисовал и показывал попап первого, забирая фокус.
* **Приватное окно** — контроллеры вкладок создаются с
  `ICoreWebView2ControllerOptions`: профиль `private`, `IsInPrivateModeEnabled`.
  Оно не пишет ни истории, ни сессии, ни паролей, ни записей о загрузках, ни
  значков закладкам. Номер его загрузки — номер операции движка со знаком
  минус; события о ней идут окну и его попапу (пузырь загрузок слушает только
  свои), а путь скачанного файла Rust помнит до выхода, чтобы файл можно было
  открыть и показать в папке. Список загрузок интерфейса держит такие записи
  сам — в базе их нет. Подсказки поисковика в нём тоже выключены.
* **Значок сайта** интерфейс получает от движка вкладки `data:`-адресом
  (`GetFavicon` по `FaviconChanged`, `Tab::wire_favicon`), а не адресом
  картинки. По адресу её загружал бы сам интерфейс — из своего, обычного
  профиля: у приватного окна это запрос к сайту с куками обычного профиля и
  след в его кэше, у обычного — второй запрос за тем, что вкладка уже скачала.
  Значок вкладка помнит и досылает окну, куда её отдали или унесли.
* **Разделённый экран** — вторая вкладка того же окна (`TabHost::set_split`):
  контейнер делится пополам, активная слева, вторая справа, обе видимы.
  Щелчок во вторую половину делает активной её (`TabEvent::Focused` от
  `GotFocus` контроллера), и вкладки при этом остаются на своих местах
  (`swapped` в `TabHost` и в `state.js`): адресная строка, горячие клавиши,
  меню страницы и её окна относятся к той половине, с которой работают.
  Вкладка не из пары встаёт на место активной половины; закрытие активной
  половины отдаёт окно второй. Rust и интерфейс считают это одинаково.
* **Группы вкладок** живут только в интерфейсе (`ui/js/tabs.js`): у вкладки
  есть имя, цвет и «свёрнута», вкладки одной группы стоят рядом, свёрнутая
  группа прячет свои вкладки и оставляет ярлык. Движок о группах не знает —
  ему всё равно, в каком порядке нарисованы вкладки. В сессии описание группы
  повторяется у каждой её вкладки (`group_json`): отдельная таблица на две-три
  группы в окне не окупается. Вкладки группы всегда стоят подряд
  (`settleGroup`): вкладка, вставшая между двумя вкладками группы (перетащили,
  Ctrl+Shift+PageUp), входит в неё, ушедшая от своей группы — выходит, ссылка из
  вкладки группы открывается в той же группе, закреплённая вкладка из группы
  выходит.
* **Место новой вкладки** — как в Chrome: Ctrl+T и «+» — в конец, вкладка,
  которую открыла страница, — сразу за ней, а фоновые (Ctrl+щелчок, средняя
  кнопка) — ещё и за теми, что эта страница уже открыла, чтобы ссылки 1, 2, 3
  легли по порядку (`openerIndex`). Среди закреплённых обычная вкладка не встаёт.
  «Закрыть другие», «слева» и «справа» закреплённые вкладки не трогают.
* Вкладки, которые не помещаются, строка прокручивает колесом, активная
  вкладка прокручивается на вид.
* Командная палитра (Ctrl+K) ищет и по открытым вкладкам окна — подстрокой в
  заголовке и адресе, только по набранному: пустая палитра — это команды.
* Размер, место и «развёрнуто» сохраняются в настройку `window_geometry`;
  каждое следующее окно сеанса встаёт со сдвигом. Место, которого нет ни на
  одном мониторе (монитор отключили), не используется — окно встаёт по центру
  (`on_screen`).
* Последняя вкладка окна закрывает само окно, как в Chrome: страницу сперва
  спрашивают «Покинуть сайт?», а в сессии окна вкладка остаётся — последнее
  окно вернётся с ней при запуске.
* Окно с идущими загрузками без вопроса не закрывается: `CloseRequested`
  откладывается (`active_downloads` хоста окна — идущие, на паузе и ждущие
  «куда сохранить»), интерфейс спрашивает «Закрыть окно?», ответ «Закрыть» —
  `window_command close_force` (`close_anyway`). «Закрыть браузер» спрашивает
  так же, по списку загрузок интерфейса.
* **Вкладку можно унести в другое окно живой** — без перезагрузки, с историей
  и введённым текстом. Вытащили из строки и отпустили за окном или ниже
  строки — новое окно у этой точки (`tab_to_window`); отпустили на строке
  другого окна — вкладка встаёт туда (тип перетаскивания
  `application/x-190x4-tab`, text/plain упал бы в поле страницы). Единственная
  вкладка окна не уезжает — переезжает само окно (`window_move`). Переносит
  `state::move_tab`: `TabHost::detach` отдаёт `Tab`, `TabHost::attach` меняет
  окну вебвью родителя (`SetParentWindow`) и переключает маршрут вкладки —
  события, окна страницы и реестр загрузок хоста лежат в `Tab` за
  `Rc<RefCell>`, обработчики движка читают их на каждом событии, а не
  запоминают при создании. Новое окно забирает вкладку само, когда его
  интерфейс готов (`launch_adopt_take` → `tab_adopt`), прежнее узнаёт
  событием `tab-moved`. Между обычным и приватным окном вкладки не ходят:
  у них разные профили движка.
* Окно, закрытое крестиком, пока открыты другие, до выхода помнится
  (`closed_windows`, до десяти): Ctrl+Shift+T, когда в окне не осталось
  закрытых вкладок, возвращает его со всеми вкладками — они встают спящими, как
  после перезапуска.
* Сессия — по окну: таблица `session_windows`, номер окна выдаётся при
  создании. Как в Chrome, окно, закрытое крестиком, пока открыты другие, при
  следующем запуске не возвращается — его сессия забывается. Последнее
  обычное окно при закрытии записывает сессию само (отложенная запись из
  интерфейса к этому моменту уже не успеет). «Закрыть браузер» в меню
  (`app_quit`) закрывает все окна разом, и возвращаются они все.
* Вкладки восстанавливают только окна прошлого сеанса (`WindowMeta::restore`):
  новое окно (Ctrl+N, вкладка в новое окно) начинается с чистого листа, даже
  если под его номером в базе что-то осталось. Перед стартом номера
  сохранённых окон выравниваются подряд (`compact_sessions`): окна получают
  номера 0, 1, 2…, а после закрытого в середине окна в базе бывают дыры.
* Ссылка из другой программы, когда открыты только приватные окна, получает
  новое обычное окно.
* Файл, брошенный на интерфейс окна (полоса вкладок, тулбар), открывается
  вкладкой: `DragAcceptFiles` + подкласс окна. Перехват перетаскивания у Tauri
  не годится — он ломает обычный HTML-drag, которым двигаются вкладки и закладки.

## Кто с кем разговаривает

| Канал | Кто | Чем |
|---|---|---|
| chrome → Rust | только chrome-вебвью | Tauri-команды (`src-tauri/src/ipc.rs`), ограничены `capabilities/default.json` |
| Rust → chrome | | `emit("tab", …)`, один поток событий, разбор по полю `kind` |
| chrome ↔ вкладка | | `PostWebMessageAsJson` в обе стороны |
| chrome ↔ попап | окно `popup` | `popup-render` → попап, `popup-action` → chrome; команды — те же Tauri-команды |
| вкладка → Rust | **только `postMessage`** | у вкладок нет ни `window.__TAURI__`, ни init-скрипта Tauri; сообщения скрипта паролей разбирает Rust, адрес отправителя — `Source()` движка |

Всё, что приходит со страницы, — недоверенный ввод: строгий разбор в enum,
никаких путей к файлам и аргументов процессов из этих данных. `postMessage`
доступен любой странице, а разбирается на главном потоке, поэтому сообщения
длиннее 64 КБ не разбираются вовсе, а в интерфейс уходят только те, что он
ждёт (`navigate`, `middle_click`, `media_found` — `for_interface`): страница,
шлющая сообщения в цикле, не загружает интерфейс браузера событиями.

**Перерисовка интерфейса — раз в кадр** (`emit` в `ui/js/state.js`). Состояние
вкладок меняется сразу, а подписчики (строка вкладок, адресная строка, панели,
запись сессии) приходят одним вызовом в `requestAnimationFrame`, перед
отрисовкой экрана. События вкладок идут пачками — загрузка страницы, счётчик
блокировок, звук, заголовки фоновых вкладок, — и раньше каждое перерисовывало
всё: 400 событий подряд стоили 400 перерисовок, теперь две. Свёрнутое окно
кадров не рисует — тогда перерисовку доводит таймер (100 мс). Кто читает DOM
сразу после изменения (место ярлыка новой группы), зовёт `flush()`. Замер
вкладок (узкие, активная на виду) — последним в той же перерисовке
(`measureTabs`). Панель блокировки перестраивается, только когда её цифры
сменились, а опрос статистики фильтра молчит, если её негде показать.

## Два правила, которые ломают интерфейс, если их забыть

**1. Нативная поверхность всегда поверх HTML.** Вкладка — это дочерний HWND
поверх окна. Любой попап chrome-а, попавший в область страницы, окажется под
ней — не «некрасиво», а буквально невидимым. Отсюда:

* боковые панели и панель закладок **отжимают** страницу (меняется трек grid →
  меняется `SetBounds`), а не накрывают её;
* меню и пузыри живут в отдельном окне `popup` поверх страницы (см.
  «Всплывающие окна»);
* командная палитра и встроенные страницы прячут нативную поверхность
  (`overlay_set`). Причин спрятать может быть несколько сразу — `layout.js`
  показывает страницу, только когда не осталось ни одной.

**2. Геометрию считает CSS, применяет Rust.** Chrome меряет `.stage` и шлёт
прямоугольник в `layout_set` вместе с `devicePixelRatio`: `SetBounds` работает
в физических пикселях, интерфейс — в CSS-пикселях. На 150% DPI расхождение
видно сразу как полоса под тулбаром.

Проверено вживую на 150% (22.09, в том числе смена масштаба у открытого окна):
страница ровно в своей области, окна страниц и меню на своих местах. Две
вещи, которые на 100% не видны: точку правого щелчка движок отдаёт в
логических пикселях, а не в физических (делёная на масштаб ещё раз, она
уезжала к углу страницы); окно попапа с тенью окружено невидимой рамкой, и
`set_position` ставит её угол — содержимое сдвигалось на её толщину.

## Адресная строка

* Адрес дописывается прямо в строке, как в Chrome (`complete`): набрали «hab» —
  в поле «habr.com», дописанное выделено. Кандидаты — история (по частоте и
  свежести) и закладки; дописывается сайт, а при «/» в набранном — адрес
  целиком; сравнение — с тем, как адрес показан (кириллицей). Дописывается
  только печать вперёд: стирание и вставка — нет. Enter ведёт туда, куда ведёт
  дописанное (со схемой из истории).
* Enter открывает то, что набрано: первая строка подсказок — переход или
  поиск набранного, закладки и история ниже, до них доходят стрелками.
  Подсказки приходят с опозданием, поэтому без выбора стрелкой Enter берёт
  текст поля, а не строку, оставшуюся от прошлой буквы.
* Схема — только в начале строки: «как настроить https://…» ищется. Путь
  Windows (`C:\…`, `\\сервер\папка`) открывается файлом, `localhost/app` и
  `192.168.1.1/admin` — по http.
* Shift+Delete на выбранной строке истории убирает её из подсказок и из
  истории.
* Слово с точкой — сайт, только если это похоже на сайт (`names_a_site`):
  известный домен верхнего уровня по списку публичных суффиксов, IP-адрес,
  порт или путь, кириллическая зона. «node.js» и «отчёт.pdf» ищутся. «? текст»
  — всегда поиск.
* Адрес показывается буквами (`displayUrl` в `dom.js`): путь без `%D0%9C…`,
  кириллический домен без `xn--`. Служебные знаки и невидимые символы остаются
  закодированными, а имя из кириллических букв, неотличимых от латиницы
  («аррӏе.com»), вне кириллических зон остаётся в виде `xn--`, как у Chrome.

## Сетевой фильтр

`WebResourceRequested` вызывается на UI-потоке для каждого запроса страницы.
Поэтому:

* матчинг синхронный, внутри — только `Guard::check`: `ArcSwap::load` (без
  локов) и `Engine::check_network_request`;
* пересборка списков — на фоновом потоке, готовый движок въезжает одним
  `ArcSwap::store`; читатели, уже вошедшие в `check`, дочитывают старый `Arc`;
* браузер стартует с пустым фильтром и не ждёт разбора списков;
* у WebView2 нет отдельного контекста для фрейма: и главная навигация, и
  документ iframe приходят как `DOCUMENT`. Различаем по адресу — у главной
  навигации он совпадает с тем, что вкладка получила в `NavigationStarting`.
  Без этого правила без модификатора типа не действовали бы на фреймы вовсе
  (`document` в их маску не входит), и рекламная врезка во фрейме проходила бы
  мимо фильтра;
* блокировка — синтетический 403: пустой для подресурсов (страницы, ждущие
  ответа от счётчика, не виснут на таймауте) и со своей страницей «заблокировано»
  для навигации;
* счётчик щита ведётся по вкладке (`TabEvent::Blocked`, не чаще раза в 300 мс)
  и обнуляется на каждой главной навигации: общий счётчик браузера живёт
  отдельно, в строке состояния;
* страницы браузера (`190x4-pages.invalid`) не фильтруются и не получают
  косметику: общие правила списков вроде `##[href*="https://dzen.ru"]` из
  RU AdList прятали плитку Дзена на новой вкладке;
* сайты без блокировки (`adblock_exempt_sites`, ключ — хост без `www.`)
  сверяются по документу вкладки, вместе с поддоменами: на таком сайте проходят
  и его запросы, и запросы встроенных в него фреймов, косметики нет. Пустой
  список стоит одной загрузки указателя. Переключают блокировку меню страницы,
  сведения о сайте и панель блокировки; действует со следующей загрузки.

Порог, за которым схему надо менять, — суммарная цена матчинга за загрузку
страницы и худший единичный вызов, а не p99 холодного старта (регулярки
компилируются лениво). Замер 12.09: на прогретом кэше p99 = 179 µs, худший
вызов 0.26 мс, вся страница — 7 мс на UI-потоке. Схема остаётся.

## Косметика и скриптлеты

Сетевой фильтр не достаёт рекламу, которую сайт отдаёт вместе со своим
содержимым: карточки в ленте, рекламу в плеере видео. Её убирают косметические
правила (`##`) и скриптлеты (`##+js(...)`).

* Расширенные списки и ресурсы скриптлетов собирает workflow `filters.yml`
  (`scripts/filters/build.mjs`) из uAssets и последнего релиза uBlock Origin и
  выкладывает в GitLab (основной источник) и в релиз `filters` на GitHub
  (prerelease, чтобы не перебить Latest обновлений браузера). Это данные под
  GPL-3.0: в репозитории их нет, лицензия — в `NOTICE.txt` выкладки.
* adblock-rust не понимает `!#if`/`!#include` и применил бы обе ветки условий;
  списки приходят уже раскрытыми под наш движок.
* Там же каждый день обновляются основные списки — EasyList, EasyPrivacy и
  RU AdList (`advblock+cssfixes`, без EasyList внутри: вариант
  `ruadlist+easylist` дублировал его правила). Они вшиты и в установщик
  (`fetch-lists.ps1`), но скачанная копия берётся вместо вшитой: иначе правила
  обновлялись бы только с выпуском браузера.
* Браузер скачивает их в `%LOCALAPPDATA%\pw.x190x4.browser\filters`
  (`filters.rs`) через 30 с после запуска и раз в 12 часов, сверяет с
  `manifest.json` по SHA-256 и пересобирает фильтр.
* Собранный движок сохраняется снимком (`engine.bin`, `Guard::snapshot`) с
  отпечатком набора (`engine.key`: версия браузера, включённые списки, размер и
  время записи их файлов). Пока отпечаток тот же, запуск поднимает снимок
  (`Guard::restore`) вместо разбора сотен тысяч правил; ресурсы скриптлетов в
  снимок не входят и кладутся заново. Сменился список — фильтр собирается и
  снимок переписывается, ключ — последним.
* Скриптлеты, подменяющие ответы сети (`trusted-*`), помечены битом прав; их
  встраивают только списки, которые браузер считает доверенными.
* На каждой навигации вкладка регистрирует скрипт документа под её адрес
  (`install_cosmetics`): скриптлеты и стиль скрытия. Скрипт сверяет хост,
  потому что встраивается во все фреймы; прежний скрипт снимается.

## Потоки

Весь COM — STA главного потока. `TabHost` и `Tab` намеренно не `Send`: их
нельзя положить в `tauri::State`. Они живут в thread-local главного потока,
команды добираются до них через `run_on_main_thread` + канал для ответа
(`src-tauri/src/state.rs`).

**Синхронная команда Tauri 2 выполняется на главном потоке**, а не в пуле.
Отсюда два правила:

* **окно создаётся только из `async`-команды.** `WebviewWindowBuilder::build`
  внутри синхронной команды на Windows — дедлок: главный поток ждёт сам себя,
  и весь интерфейс замирает (так вешало «Новое окно» в 0.2.0);
* **всё, что ходит в базу, файлы, DPAPI или оболочку Windows, помечено
  `#[tauri::command(async)]`**, а события вкладок (загрузки, иконки закладок,
  новая вкладка, ссылки на приложения) отдают такую работу в пул или в поток
  записи загрузок. На главном потоке остаются только COM-вызовы вкладок и
  раскладка. Команды, где важен порядок (`settings_set`, `session_save`…),
  интерфейс отправляет друг за другом (`ui/js/bridge.js`): в пуле два вызова
  подряд могли бы примениться наоборот.

**Сторож главного потока** (`watchdog.rs`) четыре раза в секунду ставит в его
очередь пустую задачу. Не выполнилась за секунду — сторож приостанавливает
поток, снимает стек (`RtlVirtualUnwind`) и пишет его в `browser.log`; когда
поток отпускает, пишет длительность. В релизе стек идёт адресами модуля — их
разбирает PDB из артефакта сборки `browser-symbols`; рядом с PDB (проба) —
сразу функциями и строками. `BROWSER190X4_WATCHDOG_SELFTEST=1` через пять секунд
после старта занимает главный поток на полторы секунды: так проверяется сам
сторож.

## Версии

`webview2-com` и `windows` закреплены в `[workspace.dependencies]` и обязаны

Перед бампом Tauri: `cargo tree -i webview2-com`.

Сейчас: Tauri 2.11 → wry 0.55 → webview2-com 0.38 → windows 0.61.

`adblock` — 0.13 (не 0.10: там тянется `rmp-serde 0.15`, который перестал

## Грабли первого живого запуска (12 сентября)

Четыре вещи, каждая из которых выглядела как «приложение просто не работает».

**1. Синхронно дождаться контроллера вкладки нельзя.**
`CreateCoreWebView2Controller` завершается коллбеком, и единственный способ
дождаться его на месте — вложенный насос сообщений (`wait_with_pump`). Внутри
обработчика события tao (а `run_on_main_thread` попадает именно туда) этот насос
завершения не получает: коллбек не вызывается никогда, окно при этом живое.
Поэтому `TabHost::open` выдаёт `TabId` сразу, а вкладка достраивается в
completion-коллбеке. В спайке то же ожидание работает — там свой простой цикл
сообщений, без tao.

**2. Вкладка, созданная на HWND окна, оказывается под chrome-вебвью.**
Координаты правильные, поверхность живая, на экране — ничего. Z-порядком чужих
дочерних окон (их создаёт wry) управлять нельзя, поэтому вкладки живут в
собственном дочернем окне-контейнере (`container.rs`), которое мы поднимаем
через `HWND_TOP`. Побочная выгода: раскладка — это `SetWindowPos` одного окна,
а overlay — `ShowWindow(SW_HIDE)` одного окна вместо обхода всех вкладок.

**3. Пока фокус на странице, горячие клавиши chrome не существуют.**
Нативная вкладка забирает клавиатуру себе. Клавиши браузера перехватываются на
контроллере через `add_AcceleratorKeyPressed`, помечаются `Handled` и уходят в
chrome событием `TabEvent::Shortcut`; в JS обработчик один и тот же для своих
клавиш и для пойманных во вкладке.

**4. Ctrl+F перехватывал сам движок.** У WebView2 есть собственные
акселераторы (Ctrl+F, Ctrl+P, F12): они срабатывают раньше
`AcceleratorKeyPressed`, и вместо строки поиска браузера открывался
встроенный диалог движка. Лечится `AreBrowserAcceleratorKeysEnabled = false`
в настройках вкладки — браузер здесь мы, а не движок. Всё, что делали эти
сочетания, браузер делает сам: Ctrl+F, F3 и Ctrl+G — `ICoreWebView2Find`,
Ctrl+P — `ShowPrintUI`, Ctrl+S — `ShowSaveAsUI`.

**5. У приложения нет stdout.** Сборка идёт с `windows_subsystem = "windows"`,
консоли нет, `tracing` писал в никуда — а именно в логе была видна причина
первых двух проблем. Логи пишутся в `%LOCALAPPDATA%\pw.x190x4.browser\browser.log`,
лог прошлого запуска остаётся рядом — `browser.old.log`.

И фронтовое: `[hidden]` не работает на элементе, которому CSS задал
собственный `display` — нужна строка `[hidden] { display: none !important }`
(счётчик блокировок и кнопка загрузки видео висели на экране в состоянии «ноль»).

## Грабли канонических функций (13 сентября)

**1. Горячая клавиша со страницы не переносит клавиатуру.** Ctrl+L, Ctrl+F и
Ctrl+K приходят в интерфейс событием, но фокус Windows остаётся в окне
вкладки: `focus()` на поле адреса ставит только DOM-фокус, и набранный текст
уходит на страницу. Интерфейс зовёт `chrome_focus` — `MoveFocus` на
контроллере chrome-вебвью.

**2. Возврат фокуса даёт мимолётный `blur`.** Адресная строка выходит из
режима ввода по `blur`, поэтому перед закрытием проверяет, что фокус
действительно ушёл.

**3. Высота попапа мерится до показа окна.** Всё, что привязано к высоте
окна (`100vh`), в этот момент даёт прежний размер окна, а не содержимое: меню
и пузыри обрезались. Мерится естественная высота, а Rust возвращает высоту,
которая досталась окну.

**4. Новая вкладка забирает клавиатуру.** Готовая поверхность вкладки и
`autofocus` на странице новой вкладки уводили курсор из адресной строки. Курсор
возвращается в адресную строку, когда контроллер вкладки готов.

## Грабли живой проверки (14 сентября)

**1. Нулевой символ обрезает встроенный скрипт.** `AddScriptToExecuteOnDocumentCreated`
и `ExecuteScript` принимают скрипт строкой, завершённой нулём. Символ U+0000
внутри строкового литерала молча отрезал остаток, и менеджер паролей не
встраивался ни на одной странице. Тот же текст работал в Chromium и через
`eval`, где ноль экранирован. Тест в `tab.rs` не пускает в скрипт управляющие
символы; `190x4-spike script` проверяет, какой текст движок выполняет.

**2. Браузерные сочетания движка в окне интерфейса.** Ctrl+J открывал
встроенную полку загрузок WebView2 поверх интерфейса, F5 перезагрузил бы сам
интерфейс. В окне интерфейса они выключены так же, как на вкладках.

**3. Навигация, ушедшая в загрузку, документ не меняет.** Адрес из
`NavigationStarting` оставался у вкладки: адресная строка показывала ссылку на
файл, а восстановленная сессия заново скачивала его при каждом запуске.
`Finished` несёт адрес документа, и он же снова становится источником для
фильтра и автозаполнения.

**4. `KeyboardEvent.code` берётся из скан-кода.** Ввод без скан-кода
(экранная клавиатура, удалённый доступ) даёт пустой `code`, а `key` на русской
раскладке — кириллицу. Сочетания интерфейса в этом случае читают букву из
`keyCode`.

**5. Ширина полосы вкладок бралась из содержимого.** Узкие вкладки без подписей
сжимали полосу под себя и не расширялись, когда окно разворачивали. Ширина
полосы — от числа вкладок (`--tab-count`), узкий режим пересчитывается при
изменении размера.

**6. Страница настроек не перерисовывалась после клика.** Перерисовку
пропускали, пока фокус внутри страницы, чтобы не мешать вводу, а клик по
варианту сам ставит фокус внутрь: отметки и зависимые строки не менялись.
Пропускается только ввод в поле; фокус после перерисовки возвращается на тот
же контрол.

**7. Устаревший замер попапа приходил последним.** Показ и подгонка — отдельные
команды; ответ на ранний замер пустого окна перебивал поздний, и содержимое
папки закладок обрезалось. Замеры идут очередью.

**8. Тема в попапе отставала на одну смену.** Свой слушатель события `settings`
срабатывал раньше, чем модуль настроек обновлял значение. Тема применяется по
подписке на настройки.

**9. Геттеры цели меню без флага отвечают ошибкой.** `LinkUri`, `LinkText`,
`SourceUri` и `SelectionText` при ложном флаге `Has…` возвращают 0x8000000E, а
не пустую строку, как написано в документации. Ошибка обрывала обработчик
`ContextMenuRequested` до `SetHandled`, и вместо своего меню показывалось меню
движка. Поля читаются только при флаге; сбой перехвата пишется в лог с шагом.

## Страницы ошибок

Страница движка — чужая деталь: она на языке системы, с оформлением Edge и
советами про Edge. Своя страница рисуется прямо в документе
(`crates/webview/src/errors.rs`): `NavigationCompleted` с ошибкой выполняет
скрипт, который переписывает содержимое. Адрес в строке и запись в истории
остаются прежними — так же ведёт себя Chrome, и «назад» не упирается в
страницу ошибки. Отменённая навигация (переход ушёл в загрузку, поверх лёг
новый адрес) страницы не получает.

* Страница собирается из элементов (`createElement`, `textContent`), а не
  строкой HTML: у страницы ошибки сертификата движок требует Trusted Types, и
  `innerHTML` там бросает исключение — поэтому до 0.3.1 на ошибке сертификата
  оставалась страница Edge.
* **Ошибка сертификата.** Страницу движка («Подключение не защищено») движок
  ставит сам и уже после `NavigationCompleted`, поэтому своя встаёт по
  `DOMContentLoaded` её документа (и отложенной попыткой) — только если
  `ServerCertificateErrorDetected` отметил эту страницу вкладки и перед
  скриптом действительно страница движка. «Всё равно перейти» под
  «Подробнее» зовёт механизм самой страницы движка
  (`certificateErrorPageController.proceed`), решение движок помнит до выхода.
  Сайт, открытый так, до выхода помечен в адресной строке «Не защищено»
  (`TabEvent::Insecure`, во все окна — событием `insecure-host`).

## Состояние (SQLite)

История, закладки, сессия, загрузки, настройки и пароли живут в одной базе
`%LOCALAPPDATA%\pw.x190x4.browser\browser.db` (крейт `browser190x4-store`). База
открывается в WAL: интерфейс читает историю, пока вкладки пишут визиты.
Схема версии 4: `bookmark_nodes` (дерево закладок), `settings` (ключ → JSON),
`passwords` и `password_never`, у `downloads` — поля `kind` и `error`,
`session_windows` (сессия каждого окна, с закреплёнными вкладками) и `visits`
(каждое посещение отдельной строкой). Плоская таблица закладок первой версии
переносится на панель закладок, сессия второй — в окно 0.

`history` осталась сводкой по адресу: по ней работают подсказки адресной
строки и ранжирование в SQL. Страница истории читает `visits` — без них
«сегодня в 14:20 и вчера в 9:00» показать нечем.

Кто что делает:

* **визит записывает chrome**, а не движок: только там в одном месте известны
  и адрес, и заголовок — в событиях WebView2 они приходят порознь. Посещение
  одно на загрузку страницы: смена заголовка потом (счётчик писем, таймер,
  название трека) правит только его (`history_title`), иначе сайт с часами в
  заголовке писал бы по строке в секунду. Страница с тем же заголовком, что у
  прошлой, записывается по `NavigationCompleted`;
* **ранжирование подсказок — в SQL**, а не в JS: вес «частота против
  свежести» считается там же, где лежат данные;
* **сессия сохраняется с задержкой** (800 мс) и только если изменилась:
  восстановление само порождает серию изменений, и без задержки старт
  затирал бы список, который в этот момент читает, а счётчик блокировок или
  звук вкладки сессию не меняют; при закрытии окна её дописывает Rust, а
  вкладки прошлого сеанса открываются спящими — вебвью под них заводится при
  первом показе;
* **загрузки пишет Rust** (`transfers.rs`): движок шлёт прогресс не чаще пяти
  раз в секунду, в базу он уходит раз в секунду; загрузки, шедшие в момент
  закрытия браузера, при старте помечаются ошибкой `shutdown`.

Крейт не знает ни про COM, ни про Tauri: его тесты гоняются на любой
платформе через `Store::memory()`.

## Сервисы 190x4 (переводчик и загрузчик)

Своего бэкенда у браузера нет: `/api/translate` и `/api/yt-ext/*` уже работают
на сервере 190x4, там один ключ Gemini, один rate-limit, одни логи и разобранные
грабли yt-dlp по источникам. Браузер — клиент (крейт `browser190x4-services`).

**Ключи не в коде и не в репозитории.** Конфиг —
`%LOCALAPPDATA%\pw.x190x4.browser\services.json`, для разработки его перекрывают
переменные `BROWSER190X4_TRANSLATE_KEY` и `BROWSER190X4_MEDIA_KEY`. Ключей нет и
во вкладках: все запросы делает Rust, страница к ним не прикасается.

Что выяснилось при подключении к живому API:

* **Таймаут не бывает один на всех.** Перевод — интерактивное действие
  (25 с), разбор ссылки идёт через yt-dlp и честно думает до минуты (90 с),
  файл качается сколько нужно (час). Общий 20-секундный таймаут клиента ронял
  разбор ссылки на «error sending request».
* **Чужой API кладёт `null` и пустые строки куда угодно.** `total` приходит
  пустой строкой, пока размер неизвестен; `phase` — `null`. Строгие `i64` и
  `String` роняли разбор всего ответа. Поэтому у прогресса все поля читаются
  через устойчивые десериализаторы, а не латаются по одному на каждый прогон.
* **Служебные коды сервера — не текст для пользователя.** `session_busy`,
  `unsupported_source` переводятся в человеческие фразы на стороне клиента.
  Плюс повторный клик по формату отсекается в интерфейсе: сервер держит одну
  загрузку на сессию.
* **Спецификация формата собирается в одном месте.** Сервер отдаёт
  `video_formats` и `audio_formats` раздельно, спецификацию (`video:1080`,
  `audio:192`) собирает клиент — это правило живёт в крейте, а не в UI.

**Переводчик — расширение, как DeepL**, а не боковая панель: значок на панели
инструментов открывает окно (`translate` в `ui/js/popup/main.js`), куда
вставляют или печатают любой текст. Язык оригинала — «Определить язык» (`auto`,
его определяет модель и возвращает, что распознала) или выбранный, язык
перевода — настройка `translate_lang`, оригинала — `translate_source`; оба
меняются прямо в окне, а кнопка между ними меняет языки местами и переносит
перевод в оригинал. Текст уходит переводиться сам после паузы в наборе
(650 мс) или сразу по Ctrl+Enter; тот же текст на ту же пару языков повторно
не отправляется, а ответ на устаревший запрос не рисуется. Окно закрывается
вместе с фокусом, как у расширений Chrome, поэтому черновик живёт в окне
попапа весь сеанс: открытое снова продолжает с того же текста, а ответ,
пришедший уже в новое окно, рисует оно. Текст — не длиннее 5000 знаков
(`TRANSLATE_MAX_TEXT`, его же показывает счётчик в окне).

Выделенный текст приходит в окно из меню страницы («Перевести выделенное») и
по Ctrl+Shift+U — его читает `tab_selection` скриптом в документе вкладки
(фреймы не в счёт). «Скачать через 190x4» в меню видео и Ctrl+Shift+D открывают
загрузчик для текущей страницы.

## SponsorBlock

Расширение SponsorBlock — своё, как переводчик: движок расширений Chrome в
браузер не подключён. Сегменты видео YouTube (спонсорские вставки, просьбы
подписаться, заставки) размечает сообщество SponsorBlock, данные под CC
BY-NC-SA 4.0, ссылка на них — в настройках расширения.

* Скрипт плеера (`crates/webview/src/inject/sponsorblock.js`) встраивается в
  каждый документ и фрейм, как скрипт паролей, но первой строкой проверяет хост
  и работает только на YouTube и в его плеере без кук, в том числе встроенном
  в чужую страницу. Он сообщает номер видео (`sponsorblock_video`) при загрузке
  плеера и при переходах внутри YouTube (`yt-navigate-finish`) и ждёт сегменты.
* Сеть и настройки — в Rust (`src-tauri/src/sponsorblock.rs`). Адрес
  документа берётся у движка, от страницы — только номер видео (11 знаков).
  Запрос анонимный: на сервер уходят первые четыре знака SHA-256 номера, сервер
  отдаёт сегменты всех видео с таким началом, нужное выбирается здесь. Ответ
  держится в памяти 10 минут, все категории сразу — смена настроек нового
  запроса не требует. Нужны только пропуски (`actionType` skip): метки глав,
  приглушение и «всё видео — реклама» не берутся.
* Режим категории — настройка `sponsorblock_<категория>`: `skip` — скрипт
  пропускает сам и показывает «Пропущено · Вернуть», `ask` — пока идёт
  сегмент, кнопка «Пропустить», `show` — только отметка на полосе прокрутки,
  `off`. Умолчания — как у SponsorBlock: пропускается спонсорская вставка,
  остальное отмечается, отступления и не-музыка выключены.
* Скрипт слушает события медиа на `document` при захвате (они не всплывают) и
  берёт только главное видео плеера (`html5-main-video`): превью в ленте тоже
  видео. Во время рекламы YouTube (`ad-showing`) время плеера — время ролика
  рекламы, и скрипт ничего не делает. Начало ближайшего сегмента он ловит
  таймером, а не следующим `timeupdate`, который бывает раз в четверть секунды.
  Сегмент, в который перемотали сами или вернулись по «Вернуть», до смены видео
  не пропускается. Плашка и отметки — закрытый shadow DOM в плеере, кнопки
  отвечают только на щелчок человека (`isTrusted`).

## Всплывающие окна

Меню, пузырь загрузок, правка закладки, «Сохранить пароль?», окно
расширения и окна страниц — это одно окно `popup` (`src-tauri/src/popup.rs`, `ui/popup.html`),
принадлежащее главному. HTML-слой в окне браузера не подходит: он оказался бы
под нативной страницей, а прятать страницу ради меню нельзя.

* Окно создаётся заранее, через 1,5 с после старта: первое меню не ждёт
  запуска вебвью.
* Порядок показа: chrome зовёт `popup_open` с прямоугольником кнопки → Rust
  ставит окно и шлёт `popup-render` → попап рисует, меряет себя и зовёт
  `popup_show` с высотой. Выросшее содержимое — `popup_resize`, без повторного
  показа.
* Потеря фокуса скрывает попап. Клик по той же кнопке, что его открыла,
  сначала закрывает попап (фокус ушёл в окно браузера) и лишь затем приходит
  кликом, поэтому повторное открытие того же попапа в первые 300 мс — это
  «закрыть» (`popups.js`).
* У каждого показа свой номер (`seq`): его возвращает `popup_open`, с ним
  приходит `popup-closed` (и `replaced`, если окно не пряталось, а его занял
  следующий попап), его передают `popup_hide` и `popup_show`. Закрытие меню и
  открытие следующего попапа идут разными путями, и без номера запоздавшее
  «меню закрыто» принималось за закрытие нового: «Закрыть браузер?» отвечало
  «нет» само, меню страницы переставало выполнять команды. Скрыть можно только
  текущий показ, а показ, который уже закрыли или сменили, на экран не выходит
  (подсказки, по которым успели нажать Enter). Окно страницы, которое занял
  другой попап, возвращается, когда тот закроется.
* Перемещение и изменение размера главного окна закрывают попап.
* Короткие сообщения («Скачано», «страница перестала работать») без строки
  состояния — тоже попап, показанный без фокуса у нижнего края страницы
  (`toast`): HTML-плашку над сайтом закрыла бы нативная страница. Меню и
  пузыри сообщение не сменяет, а окно страницы (alert, разрешение) — сменяет.
  Строка состояния и боковая панель по умолчанию скрыты, как в Chrome: цифры
  фильтра — телеметрия, а не то, что человек смотрит каждый день.
* Значок загрузчика видео на панели, пункты «Скачать через загрузчик 190x4» и
  «Перевести выделенное» в меню страницы появляются, только когда сервисы
  настроены (`services_state`): без ключа они лишь сказали бы, что не
  работают. Ctrl+Shift+D, палитра и настройки по-прежнему объясняют, что нужно.
* Подсказки адресной строки — тот же попап, но показанный без активации
  (`SW_SHOWNOACTIVATE`): клавиатура остаётся в адресной строке, стрелки двигают
  выделение событием `suggest-select`. Видимостью попапа Rust управляет через
  Win32, а не через `show()`/`hide()` Tauri: tao помнит свой флаг видимости и
  пропустил бы следующий показ после скрытия в обход него.
* Тот же попап на прежнем месте (подсказки на каждую клавишу) получает только
  новое содержимое: окно не переезжает, не сжимается до черновой высоты и не
  показывается заново, поэтому не мигает.
* Меню страницы по правому щелчку — тоже этот попап. `ContextMenuRequested`
  помечается обработанным и держится отсрочкой; движок отдаёт свои пункты
  (имя, подпись, номер команды, состояние) и цель щелчка, `context-menu.js`
  собирает из них меню со своими пунктами (поиск, перевод, загрузчик видео,
  блокировка на сайте). Команду движка попап отдаёт движку сам
  (`SelectedCommandId`), и только потом закрывается: иначе закрытие успело бы
  ответить «без выбора». У каждого меню свой номер — ответ на устаревшее меню
  ничего не делает. Подменю движка («Другие инструменты») не показываются: они
  открывают окна Edge. Меню у точки щелчка раскрывается вверх, если снизу не
  помещается (`align = "point"`).

## Окна, которые открывает страница

`window.open`, ссылка с `target=_blank` и «Открыть ссылку в новой вкладке»
приходят событием `NewWindowRequested`. Окно движка браузеру не нужно — окно
становится вкладкой, но **настоящей**: движок ждёт её под отсрочкой
(`TabEvent::Popup` с номером окна), `tab_open` с этим номером создаёт вкладку и
отдаёт её странице через `SetNewWindow`, а навигацию ведёт сам движок. Без
этого `window.open` возвращал странице `null`: вход через Google, VK ID,
Telegram и Яндекс ID, который ждёт ответа от своего окна (`window.opener`,
`postMessage`), не заканчивался. Вкладка отдаётся окну только после того, как
встроился скрипт паролей, — иначе первый документ окна входа остался бы без
него.

* **Окна без щелчка не открываются.** Встроенный блокировщик Edge в WebView2
  выключен; `IsUserInitiated` ложный — окно открыл скрипт сам по себе
  (реклама поверх страницы). Такое окно получает отказ (`tab_popup_deny`), а у
  адресной строки появляется значок: окно можно открыть или разрешить сайту
  открывать окна всегда (настройка `popups_allowed_sites`, список — в
  «Конфиденциальности»).
* Ctrl+щелчок по ссылке открывает вкладку в фоне: в момент события Ctrl ещё
  зажат (`GetAsyncKeyState`). Средняя кнопка — тоже в фоне: к событию она уже
  отпущена, поэтому о нажатии по ссылке заранее сообщает встроенный скрипт
  (`middle_click`), и окно, открытое в следующие 1,5 с, встаёт фоном.
* `window.close()` из такого окна (`WindowCloseRequested`) закрывает вкладку и
  возвращает фокус странице, которая её открыла.
* Вкладка, чья первая навигация ушла в загрузку файла, закрывается сама: у неё
  нет документа (`Source` пуст или `about:blank`). Так же повтор загрузки
  открывает ссылку фоновой вкладкой, а не уводит страницу, открытую у
  пользователя.
* Закрыли вкладку раньше, чем движок её достроил, — контроллер закрывается в
  коллбеке, а события уже закрытой вкладки интерфейс не пускает в строку
  (`markClosed` в `state.js`): иначе она возвращалась бы призраком.

## Новая вкладка без рывка

Новый вебвью показывается не сразу: контроллер создаётся асинхронно, до
первой отрисовки движок заливает его белым, а страница новой вкладки
грузится с нуля и дорисовывается по частям. Покадровая съёмка Ctrl+T до
исправления: страница пропадает, пустой кадр, белый кадр во всю область,
тёмный, затем новая вкладка в два шага — «вкладка вписывается в окно».

* **Прогретая новая вкладка** (`TabHost::prewarm`, `spare`): у каждого окна
  одна новая вкладка создаётся заранее, невидимой, и уже нарисована. Её нет в
  `order`, её события не уходят в интерфейс (`announced`), кроме сообщений
  страницы — новая вкладка в это время уже просит плитки и погоду. Ctrl+T и
  «+» забирают её (`adopt_spare`, `announce` досылает интерфейсу пропущенное),
  следующая прогревается через 0,4 с (`tab_prewarm`).
* **Передача экрана**: вкладка, которая ни разу не была на экране, рисует
  первый кадр за 2–3 кадра. Поэтому её окно опускается под прежнюю вкладку
  (`container::lower`), а прежняя прячется через 120 мс (`HANDOVER_MS`,
  таймер `later.rs`). Окно вкладки внутри контейнера находится после создания
  контроллера (`remember_window`). Переключение между уже показанными
  вкладками движок и так делает за кадр — у них остаётся последний кадр.
* **Цвет до первой отрисовки** — цвет темы: движку до создания контроллера
  (`WEBVIEW2_DEFAULT_BACKGROUND_COLOR`) и контроллеру (`SetDefaultBackgroundColor`).
  На навигации к сайту он становится белым: страница без своего фона должна
  быть белой, а не тёмной.
* Страница новой вкладки с первого кадра в цвете темы (`newtab.html`, тему
  помнит `localStorage`) и показывается целиком, когда есть плитки и шрифты
  (`data-boot`, не дольше 0,5 с).
* Часы новой вкладки — стопка SVG-слоёв (`hud__layer`): кольца и маркер
  секунд вращаются целыми слоями, это делает композитор. Пока вращались
  группы внутри одного SVG, открытая новая вкладка перерисовывала весь
  циферблат с тенями каждый кадр (замер в headless Chromium: 8% главного
  потока и 20 пересчётов раскладки в секунду; слоями — 4% и один пересчёт в
  секунду, на смену цифр). Пульс «сейчас» у монитора ресурсов — тоже
  `transform` и `opacity`, а не тень.
* Но любое бесконечное движение — это кадр на каждое обновление экрана: на
  мониторе 165 Гц живой HUD стоил 55–60% ядра, пока вкладка на виду, со
  скачком раз в секунду — около 6%, совсем статичный — около 1%. Поэтому HUD живой (`data-hud="live"`) первые 10 секунд
  после показа вкладки и пока двигают мышью, крутят колесо или печатают, а
  потом спокойный (`calm`): кольца, пол и развёртка замирают
  (`animation-play-state: paused`, без скачка при пробуждении), дуга секунд
  и маркер двигаются скачком, двоеточие и пульс «сейчас» не мигают, глитча нет.
  Спрятанная вкладка сразу спокойная, а её часы стоят (прогретая вкладка
  каждого окна и новые вкладки в фоне): при показе они сразу встают на время.
* Дуга секунд растёт переходом `stroke-dashoffset` — это перерисовка её слоя с
  тенью, композитор такой переход не ведёт. Плавный переход перерисовывал дугу
  с частотой экрана, поэтому он ступенчатый: двенадцать шагов в секунду, сдвиг
  меньше пикселя. Маркер и кольца едут композитором.
* Карточки и поиск — без размытия фона (`backdrop-filter`): под ними едет сетка
  пола, и размытие пересчитывалось на каждом кадре и после каждого обновления
  монитора ресурсов. Подложка плотнее (`--glass`), на глаз разницы нет, а
  спокойная новая вкладка в замере с программной отрисовкой стоит 10% ядра
  вместо 27%.
* Состояние страница получает при каждом показе, а плитки пересобирает, только
  если сменились они или тема: иначе подложки значков мигали.

## Закрытие вкладки и «Покинуть сайт?»

`Controller.Close` обработчик `beforeunload` не зовёт, а своего вызова для
этого у движка нет. Поэтому вкладку сначала уводят на `about:blank`
(`Tab::request_close`): страница с несохранённым текстом просит «Покинуть
сайт?», остальные отпускают сразу, и начало этой навигации значит «можно
закрывать» — она отменяется, а интерфейс получает `close_confirmed`.
«Остаться» — `close_cancelled`. Вкладка уходит из строки и с экрана сразу
(`closing` в `state.js`), не дожидаясь ответа; если страница спросила,
вкладка возвращается на место с этим окном. Страница, которая не ответила за
1,5 с и окна не показала, закрывается. Спящие и встроенные вкладки
закрываются без вопроса.

Окно (крестик, Alt+F4, панель задач, Ctrl+Shift+W) спрашивает так же каждую
свою страницу: `CloseRequested` откладывается, интерфейс получает
`close-asked`, спрашивает страницы разом (`confirmWindowClose`), и окна
«Покинуть сайт?» встают по одному, каждое над своей вкладкой. «Остаться» на
любой — окно остаётся, остальным страницам отвечаем «Остаться». Согласие —
`window_command close_asked`, дальше Rust спрашивает только про загрузки.
Интерфейс, который не ответил (завис), окно не держит: повторное закрытие
позже 8 с проходит без вопроса страницам.

## История «Назад» и «Вперёд»

Правый щелчок или долгое нажатие на «Назад»/«Вперёд» открывает список страниц
вкладки. Своего вызова у движка нет — список и переход берутся из протокола
отладки: `Page.getNavigationHistory` и `Page.navigateToHistoryEntry` через
`CallDevToolsProtocolMethod` (так же, как перезагрузка мимо кэша). Значки —
только из кэша профиля (`site_icon`).

## Усыпление вкладок

Вкладка, которую давно не открывали (настройка `tabs_sleep`, по умолчанию
час), засыпает — как спящие вкладки Edge: `TrySuspend` замораживает страницу, а
`MemoryUsageTargetLevel = LOW` отдаёт часть памяти. История, прокрутка и
введённый текст остаются; показ будит вкладку сам, уровень памяти
возвращается в `set_visible`. Не засыпают закреплённые вкладки (почта,
мессенджеры), играющие звук, ещё не загрузившиеся и упавшие; страницу со
звуком движок не усыпляет и сам. Таймер и отметка `frozen` — в `tabs.js`.

## Звук и SmartScreen

Без своих аргументов wry передаёт движку
`--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection
--autoplay-policy=no-user-gesture-required`: SmartScreen выключен, а сайты
включают звук без щелчка. Браузер передаёт свои (`init_browser_args`), одни на
все вебвью процесса — окна и попапы делят окружение WebView2, и вебвью с
другими аргументами движок не создаст:

* SmartScreen в движке включён, вкладкам его включает и выключает настройка
  `smartscreen` (`ICoreWebView2Settings8::IsReputationCheckingRequired`,
  сразу для открытых вкладок); окна интерфейса SmartScreen не проверяет.
* Звук — как в Chrome: `document-user-activation-required`, видео со звуком
  играет после щелчка или клавиши на странице. Настройка `media_autoplay`
  возвращает прежнее поведение; аргументы читаются при запуске, поэтому она
  действует после перезапуска.

## Упавшая страница и упавший движок

`ProcessFailed` вкладки (`TabEvent::Crashed`):

* **Процесс страницы упал** (`exited`) — на её месте страницу ошибки ставит сам
  движок. Вкладка помечается значком предупреждения и при следующем показе
  загружается заново, как в Chrome; щелчок по упавшей активной вкладке делает
  то же.
* **Страница зависла** (`unresponsive`) — сообщение в строке состояния, не
  чаще раза в полминуты: движок повторяет событие, пока страница висит.
* **Упал весь движок** (`browser`) — вместе с вкладками умер и интерфейс окон,
  вернуть их может только новый процесс (`relaunch_after_engine_crash`).
  Браузер запускает себя заново и выходит; новый процесс ждёт выхода прежнего
  (`BROWSER190X4_WAIT_PID`), иначе застал бы его живым и отдал бы ему адреса
  как повторный запуск. Вкладки возвращаются из сессии. Один раз за процесс и
  не в первые полминуты: падение на старте перезапуском по кругу не лечится.

## Во весь экран

Движок только сообщает, что у страницы появился полноэкранный элемент
(`ContainsFullScreenElementChanged`, кнопка плеера). Всё остальное делает
браузер (`ui/js/fullscreen.js`): окно — `set_fullscreen`, интерфейс прячется
(`data-fullscreen`), и `.stage` занимает окно целиком. Escape на странице
сворачивает видео (`AcceleratorKeyPressed`, только пока элемент развёрнут),
переключение вкладки — тоже. Разделённый экран на время видео снимается и
возвращается после. Несколько секунд сверху висит подсказка «Чтобы выйти из
полноэкранного режима, нажмите Esc» (F11 — для окна): это попап, показанный
без фокуса (`hint`), — Escape остаётся у видео. F11 — то же без видео: окно без интерфейса до
повторного F11.

## Окна страниц

alert, confirm, prompt, «Покинуть сайт?», запросы разрешений, вход на сайт по
паролю (HTTP Basic, NTLM) и открытие приложения по ссылке рисует браузер, а не
движок (`crates/webview/src/dialogs.rs`, `ui/js/dialogs.js`).

* Движок отдаёт запрос и ждёт ответа под отсрочкой: `ScriptDialogOpening` (окна
  движка выключены `AreDefaultScriptDialogsEnabled`), `PermissionRequested`,
  `BasicAuthenticationRequested`. У окна свой номер во вкладке; ответ —
  `tab_dialog` с номером, после него Rust сообщает `dialog-done`.
* Окно — тот же попап (вид `dialog`), но потеря фокуса его не закрывает, а при
  перемещении окна браузера оно едет вместе с ним. Если окно сменило меню,
  закрыл ресайз, свернули окно или переключили вкладку, `dialogs.js` покажет его
  снова: у каждой вкладки своя очередь, окно встаёт только над страницей своей
  вкладки и только когда другой попап закрыт.
* alert, prompt и вход на сайт — над страницей своей вкладки по центру (в
  разделённом экране — над своей половиной); разрешение активной вкладки —
  пузырём у сведений о сайте в адресной строке. Камера и микрофон одного сайта
  — одним окном.
* Разрешение: «при посещении сайта» и «никогда» движок сохраняет в профиле
  (`SavesInProfile`), «в этот раз» и закрытое окно — нет. Закрытое окно —
  отказ: состояние `DEFAULT` вернуло бы окно движка. Вид разрешения, которого
  браузер не знает, остаётся окну движка. Сохранённые решения и их сброс — в
  «Конфиденциальности» (`GetNonDefaultPermissionSettings`, `SetPermissionState`).
* Со второго окна страницы можно запретить ей новые окна: до следующей
  навигации она получает ответ сразу. Навигация отвечает отказом на все ждущие
  окна прежней страницы, кроме «Покинуть сайт?» — навигация, ради которой оно
  показано, начнётся только после ответа.
* Кнопки разрешения и открытия приложения оживают через 500 мс после показа:
  страница не должна подсунуть окно под двойной щелчок.
* Ссылку на приложение (`LaunchingExternalUriScheme`) движок отменяет сразу,
  решает `src-tauri/src/external.rs`. Опасные схемы (`javascript`, `file`,
  `ms-msdt`, `search-ms`…) и адреса длиннее 2048 символов не открываются вовсе;
  название приложения — `AssocQueryStringW`; открывает `ShellExecuteW` с
  адресом в кавычках в отдельном потоке. Окно браузера отвечает номером — адрес
  со страницы в интерфейс не уходит. «Всегда разрешать» — только сайтам по https
  и только для ссылок по щелчку; список — настройка `external_apps_allowed`.

## Встроенные страницы

`190x4://settings`, `190x4://downloads` и `190x4://history` — вкладки без
WebView2: их рисует chrome на месте страницы, пока нативная поверхность скрыта
(подход Vivaldi).
Команды браузера доступны им напрямую, а сайт не может открыть их фреймом или
переходом. Такие вкладки есть только в JS-модели (`tabs.js`, id от 1 000 000),
сохраняются в сессию и существуют в одном экземпляре.

Новая вкладка — наоборот, обычная вкладка WebView2 на
`http://190x4-pages.invalid/newtab.html` (папка `pages`, virtual host). IPC Tauri
у неё нет: запросы `newtab_*` уходят `postMessage` в `newtab.rs`, ответы — через
`PostWebMessageAsJson`. Принимаются они только от страниц браузера, а ответ
уходит, только если вкладка всё ещё на странице браузера: в отчёте о ресурсах
заголовки других вкладок.

* Плитки (`newtab_tiles`) хранит база; адрес — только http(s). Значки —
  `site_icons.rs`: `apple-touch-icon`, `<link rel=icon sizes>`, SVG и иконки
  манифеста, ближайший к 180 px, последним — `/favicon.ico`. Тип картинки
  определяется по содержимому. Значок хранится в профиле неделю (`site-icons`),
  отсутствие значка — сутки.
* Погода — `weather.rs`. Место — выбранный город (`newtab_city`) или
  найденное автоматически: служба расположения Windows (по Wi-Fi, прокси на неё
  не влияет), без неё — IP-адрес. Название по координатам — OpenStreetMap,
  прогноз и поиск городов — Open-Meteo. Координаты уходят округлёнными до сотых.
* Монитор ресурсов — `resources.rs`. Браузер — наш процесс и все его потомки;
  роли и страницы процессов сообщает движок (`GetProcessExtendedInfos`), iframe
  засчитывается странице, в которую встроен. Память — частный рабочий набор,
  процессор — время всех ядер за интервал между замерами, видеокарта — счётчики
  PDH `GPU Engine` (у процесса — самый загруженный тип движка) и
  `GPU Process Memory`, как в диспетчере задач Windows. Страница спрашивает раз
  в две секунды, пока видима (счётчики видеокарты перебирают все процессы
  системы — монитор не должен сам грузить машину); замер свежее 0,7 с
  отдаётся из кэша.

## Закладки

Дерево с двумя корнями: «Панель закладок» (id 1) и «Другие закладки» (id 2),
переименовать и удалить их нельзя. Порядок в папке — `position` без дыр.
Ctrl+D и звезда сохраняют закладку сразу, пузырь меняет название и папку;
папка по умолчанию — последняя выбранная.

Импорт и экспорт — HTML в формате Netscape (`bookmarks_html.rs`), его понимают
все браузеры. При импорте панель закладок из файла заполняет нашу панель, если
та пуста, иначе уходит в папку «Импортировано»; повторы в той же папке
пропускаются. Экспорт пишет иконки только `data:`-URI.

Из Chrome, Edge, Яндекс Браузера, Brave, Vivaldi и Opera на том же компьютере
закладки и история переносятся без файлов (`import.rs`): профили ищутся в
известных папках, имена — из `Local State`, закладки читаются из JSON
`Bookmarks` (`browser190x4_store::chromium`) и ложатся тем же импортом, что
HTML. История — из копии базы `History` (браузер держит её открытой, вместе с
журналом `-wal`), за 90 дней и не больше 20 000 посещений; переходы во фреймах
не переносятся, повторный перенос не удваивает ни счётчики, ни посещения.
Профиль интерфейс выбирает по имени папки, путь Rust ищет сам. Пароли так не
перенести: Chrome и Edge шифруют их ключом, привязанным к своему exe, — для
них остаётся CSV.

## Пароли

* Скрипт `crates/webview/src/inject/passwords.js` встраивается в каждый
  документ и каждый фрейм (без строк-комментариев) и сообщает факты: «есть форма
  входа», «отправлен логин», «форма исчезла», «выбрана учётка». Сообщения
  фреймов идут через `FrameCreated` и `ICoreWebView2Frame2`, ответ уходит в тот
  же фрейм (`Tab::post_to`).
* Сайт определяется по `Source()` сообщения, то есть по данным движка; текст
  сообщения на это не влияет.
* Предложение сохранить появляется после навигации или исчезновения формы.
  Сообщение и начало навигации приходят разными путями, поэтому навигация за
  1,2 с до сообщения тоже считается подтверждением.
* Пароли шифруются DPAPI текущего пользователя с дополнительной энтропией
  (`vault.rs`). В интерфейс уходит только сайт и логин; открытым текстом —
  только по «показать», «скопировать» и при экспорте, и каждое из этих
  действий подтверждается входом Windows Hello (`hello.rs`, подтверждение
  действует минуту). Если Hello в системе не настроен, спрашивать нечем —
  действие проходит как раньше.
* Учётку, которую браузер подставляет сам, страница получает только после
  первого касания: пароль не должен лежать в поле у страницы, которую открыли
  и забыли. Выбранная человеком учётка подставляется сразу.
* Значки сайтов в списке паролей и в истории берутся из кэша профиля, а не с
  самих сайтов: иначе открытый список рассылал бы запрос на каждый сайт, где
  есть пароль, и по этим запросам был бы виден весь список.
* Учётки страницы — сохранённые для этого адреса и для других адресов того же
  сайта: регистрируемый домен по списку публичных суффиксов (`psl`), только
  https и без порта (`passwords_csv::same_site`). Свой адрес идёт первым. Во
  фрейме к ним добавляются учётки сайта вкладки (почта Mail.ru входит во фрейме
  VK ID), затем — сайтов с общим входом (`SHARED_SIGN_IN`: vk.com, vk.ru,
  mail.ru, ok.ru).
* Список учёток уходит документу без паролей и показывается под полем по
  щелчку: закрытый shadow DOM в верхнем слое (popover), методы DOM скрипт берёт
  до скриптов страницы, выбор принимается только от события `isTrusted`. Rust
  подставляет только учётку из списка, показанного этому документу, и сверяет
  адрес документа (во фрейме — скрипт по `location.origin`).
* Сам браузер подставляет учётку, только если учётка своего сайта одна и
  страница похожа на вход: есть поле пароля, `autocomplete="username"` или
  адрес вида login/auth/account. Из нескольких учёток выбирает человек.
* Вход в два шага (сначала только логин) узнаётся по полю логина без поля
  пароля: `autocomplete="username"`, `type="email"` или имя поля (email, login,
  user…). Скрипт спрашивает учётки на каждом
  шаге и помнит логин первого шага, чтобы сохранить пароль со второго.
* Новый пароль для учётки того же сайта с тем же логином обновляет её, а не
  заводит копию под новым адресом.
* Импорт CSV разбирает столбцы по заголовку (Chrome, Firefox, Bitwarden), экспорт
  пишет формат Chrome.
* Скрипт живёт в каждом документе, поэтому на странице без входа почти ничего
  не делает: щелчки и Enter разбирает, только если форму входа уже узнали или
  на странице есть поле пароля (поиск формы обходит DOM и пересчитывает
  раскладку), а видимость поля проверяет последней. За DOM он следит первые
  15 с; форму, открытую позже, узнаёт по фокусу в поле логина или пароля, и
  список учёток показывается, как только придёт.

## Загрузки

Движок знает загрузку по номеру операции в реестре хоста
(`crates/webview/src/downloads.rs`), интерфейс — по номеру записи в базе,
связка живёт в `transfers.rs`. События загрузки приходят через вебвью вкладки:
закрой её — файл докачается, но о конце никто не узнает, и запись навсегда
останется идущей. Поэтому закрытая вкладка с идущей загрузкой пропадает из
строки и с экрана, а вебвью живёт невидимым, пока загрузка не кончится
(`TabHost::close`, `parked`). Пауза, продолжение и отмена идут в
`ICoreWebView2DownloadOperation`; оборванная загрузка остаётся в реестре, если
движок умеет её продолжить. Папка и «всегда спрашивать» применяются в
`DownloadStarting` через `SetResultFilePath` и отложенное решение
(`GetDeferral`) без перезапуска. Загрузки через загрузчик видео попадают в тот
же список с `kind = media`; их отмена идёт на сервер (`/api/yt/cancel`).
Навигация, ушедшая в загрузку, документ вкладки не меняет: адрес вкладки
приходит с `NavigationCompleted`.

## Оформление

Интерфейс говорит языком HUD новой вкладки: вместо скруглений — срезанный по
диагонали угол, по краям панелей — уголки-скобки, подписи разделов —
моноширинные заглавные с ромбом, у активного — кромка акцента. Всё это —
токены в `ui/styles/tokens.css` (`--clip-tab`, `--clip-panel`, `--clip-btn`,
`--brackets`, `--hairline`, `--scan`, `--spill`) и статичные фоны: ни одна
деталь chrome-а не анимируется сама, отрисовка просыпается только от действий.

* Вкладка: тело со срезанным правым верхним углом — псевдоэлемент `::before`
  (срез на самой вкладке обрезал бы рамку фокуса), кромка по верху и по срезу —
  его же фоном. Номер вкладки — счётчик CSS в `::after` с `order: -1`; у тесных,
  узких и закреплённых вкладок его нет. У вкладки группы кромка и полоска —
  цвета группы (`--edge`).
* Кнопки-иконки: подложка при наведении — псевдоэлемент со срезом, у кнопок
  с текстом срез на самой кнопке, а рамка по срезу дорисована фоном и рамка
  фокуса — внутри.
* Уголки-скобки — фоном поверх рамки (`background-origin: border-box`), поэтому
  цвет фона задаётся отдельно (`background-color`).
* Всплывающее окно просит у Windows 11 прямые углы
  (`DWMWA_WINDOW_CORNER_PREFERENCE`, `popup::square_corners`): скругление
  срезало бы уголки-скобки.
* Кольцо загрузок и колесо загрузки вкладки — из сегментов (маска
  `repeating-conic-gradient`), полоса прогресса — тоже (`repeating-linear-gradient`).
* Приватное окно: `data-private` на `<html>` — токены меняют акцент на синий,
  у строки вкладок полоса сверху, у меню метка «Приватное».

## Иконки

* Интерфейс — свой набор 190x4: `scripts/icons/build_sprite.py` рисует его
  в коде (линия по сетке 20×20, прямые концы и острые стыки, срезанные углы,
  квадраты вместо точек) и собирает спрайт `ui/assets/icons.svg`. Один рисунок
  служит размерам 20, 16 и 12 px: у символа своё окно просмотра и толщина
  линии, на экране она около 1,3 px. Залитый вариант — контур и полупрозрачная
  заливка формы.
* Кнопки окна нарисованы по геометрии глифов Windows 11.
* Значки новой вкладки — спрайт `pages/icons.svg`
  (`scripts/icons/build_pages_sprite.py`): интерфейсные — из того же набора,
  погодные — Fluent UI System Icons (Microsoft, MIT, `pages/icons.LICENSE`).
* Иконка приложения — «глобус-маска»: багровая сфера с меридианами и тёмный
  силуэт они-маски 190x4 (`scripts/icons/build_app_icon.py`, нужен
  `rsvg-convert`). До 32 px — упрощённый вариант без мелких меридианов; из него
  же `ui/assets/brand/mark-32.png` для заголовка окна и адресной строки.
* Значок окна Tauri берёт из первой записи `icon.ico`, поэтому первой в файле
  идёт 32 px. Для панели задач и Alt+Tab браузер после создания окна ставит
  значки из ресурса exe (32512) под размеры текущего DPI (`apply_window_icon`).

## Обновления

Схема та же, что у Ninety. Установщик NSIS ставит браузер для текущего
пользователя в `%LOCALAPPDATA%\190x4 Browser`. Профиль лежит отдельно — в
`%LOCALAPPDATA%\pw.x190x4.browser`, рядом с данными WebView2 (`EBWebView`), и
флажок «удалить данные» при удалении программы чистит именно его. Профиль из
прежней папки переносится при первом запуске.

* `plugins.updater.endpoints`: сначала GitLab Generic Packages
  (`pathetix/190x4-browser`, `stable/latest.json`), затем GitHub Releases.
  Подпись установщика плагин сверяет с `plugins.updater.pubkey`.
* `updates.rs` проверяет обновления через 20 с после запуска и раз в шесть
  часов (настройка `updates_auto`) и сообщает интерфейсу `update-available`.
  Интерфейс показывает кнопку «Обновить» на панели, пункт в меню и блок в
  «О браузере»; установка — по кнопке.
* На Windows плагин запускает установщик в пассивном режиме и завершает
  браузер; установщик ставит новую версию и запускает её. Сессия сохраняется
  перед установкой.
* Сборка и выкладка — `.github/workflows/build.yml` по тегу; порядок релиза —
  `RELEASING.md`.

## Браузер по умолчанию

Назначить себя браузером программа в Windows не может: выбор хранится в
`UserChoice` под хешем, который пишет только система. Браузер регистрируется в
HKCU и открывает свою страницу в параметрах
(`ms-settings:defaultapps?registeredAppUser=190x4%20Browser`), где выбор
подтверждает пользователь. Регистрация — `default_browser.rs`.

* В реестре: ProgID `Browser190x4HTML` с командой
  `"…\190x4-browser.exe" --single-argument "%1"`,
  `Clients\StartMenuInternet\190x4 Browser\Capabilities` (http, https, .htm,
  .html, .shtml, .xht, .xhtml, .svg, .webp, .pdf), значение в
  `RegisteredApplications` и `OpenWithProgids` для «Открыть с помощью».
* Установщик регистрирует браузер после установки (`--register-browser`,
  `src-tauri/windows/hooks.nsh`), удаление снимает регистрацию
  (`--unregister-browser`), обновление её не трогает. Кнопка «Использовать по
  умолчанию» в настройках регистрирует заново — с текущим путём к exe.
* Назначен ли браузер — `IApplicationAssociationRegistration::QueryCurrentDefault`
  для http и https. Настройки перепроверяют это раз в 1,5 с три минуты после
  нажатия кнопки.
* Браузер — один процесс. Повторный запуск передаёт аргументы первому через
  `tauri-plugin-single-instance` и выходит; окно первого выходит вперёд. До
  выхода второй процесс не трогает профиль (свой мьютекс
  `pw.x190x4.browser-primary`): лог открывается с обрезкой, а незавершённые
  загрузки при старте помечаются прерванными.
* Адреса запуска — `launch.rs`: http(s) и file как есть, путь к существующему
  файлу — file-адресом, всё после `--single-argument` — один адрес (плагин режет
  аргументы по `|`, части склеиваются обратно). Очередь забирает chrome
  (`launch_take`) после восстановления сессии и по событию `launch`. Если
  браузер запустили ссылкой, пустая новая вкладка не открывается.

## Отдельный профиль и порт отладки

`BROWSER190X4_PROFILE=<папка>` запускает браузер с отдельным профилем: база, лог
и данные движка (`WEBVIEW2_USER_DATA_FOLDER`, если не задан) лежат в этой папке,
браузер не объединяется с уже запущенным и не переносит старый профиль. Вместе
с ним `BROWSER190X4_DEBUG_PORT=<порт>` открывает движку порт отладки (CDP).
Переменная `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` и политика WebView2 порт не
включают: аргументы движка передаёт само приложение (`browser_args`, см. «Звук и
SmartScreen»). Поэтому окно браузера создаётся в `setup` из описания в
`tauri.conf.json`, а попап получает те же аргументы — окна делят одно
окружение WebView2.

`190x4-spike check --url <страница> --requests <json> --downloaded <фильтры>`
проверяет снятые в Chromium запросы страницы теми же списками, что у браузера.

Свои исправления поломок сайтов лежат в `scripts/filters/190x4-fixes.txt`:
сборка фильтров дописывает их в конец `ubo-unbreak.txt`, и правка доходит до
браузеров обновлением фильтров, без выпуска браузера.

## Чего ещё нет

| Тема | Состояние |
|---|---|
| Перевод всей страницы | переводчик переводит вставленный и выделенный текст, страницу целиком — нет |
| Дубликат вкладки с её историей | список переходов читается протоколом отладки, но записать его в новую вкладку нечем — дубликат открывается с текущего адреса |
| Автозаполнение адресов и карт | не начато |
| Синхронизация между устройствами | не начато |
| Общая косметика по классам и id | скрываются элементы по правилам для сайта; правила без сайта (`##.ad`) — нет |
| Расширения Chrome | движок загружает распакованные расширения, но без кнопок и всплывающих окон на панели; не подключено |
